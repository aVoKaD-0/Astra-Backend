# Обоснование выбора и реализации

## Выбор СУБД

Для организации хранения связанных данных и обеспечения одновременной работы загрузчика и API я выбрал PostgreSQL. Фильтрация и агрегация выполняются непосредственно в базе, внешние ключи обеспечивают целостность связей между таблицами.

## Структура хранения данных

Так как одни и те же недельные показатели относятся ко многим продажам, я принял решение вынести их в отдельную таблицу и использовать внешние ключи - это сокращает избыточность данных. Изменение данных недели также отражается на всех связанных продажах. В свою очередь загрузчик сначала сохраняет показатели недели, затем продажи. 

Так как я использовал внешние ключи, создать продажу до загрузки показателей недели нельзя, по этой причине в приложении реализована проверка, которая при отсутствии недели выдаёт понятное сообщение об ошибке. Такое же правило поддерживается и на уровне БД при помощи внешних ключей.

Для хранения денежных значений я применил `Decimal` в Python и `Numeric` в PostgreSQL. Выручка и календарные поля рассчитываются в API на основе исходных данных, а импортёр проверяет их соответствие значениям из CSV - это позволяет обнаруживать несогласованные данные до записи в БД.

## Механизм инкрементальной загрузки

Поскольку у продаж отсутствует постоянный идентификатор в исходных данных, для обнаружения повторов я использовал хеш SHA-256 нормализованных полей продажи вместе с номером её повторения внутри файла. Нормализация позволяет считать одинаковыми значения с разным представлением, например `0.1` и `0.10`, а номер повторения нужен, чтобы сохранить несколько одинаковых продаж в одной выгрузке.

Ключи загруженных записей я решил хранить в отдельном журнале импорта - это позволяет пропускать известные продажи при повторных выгрузках. Для недельных показателей ключом служит дата недели, при повторной загрузке существующая запись обновляется.

Подход имеет ограничение: новую продажу, полностью совпадающую со старой и поступившую отдельной выгрузкой, невозможно отличить от повтора, а исправленная строка с другими значениями будет считаться новой продажей. Для точного различения этих случаев нужен постоянный идентификатор операции от источника.

## Организация загрузки CSV

Для экономии памяти я решил читать CSV построчно, а данные записывать пакетами. Весь запуск импортёра выполняется в одной транзакции, если возникает ошибка, изменения откатываются, чтобы в базе не оставалась частично загруженная выгрузка. Из минусов — длительная транзакция при обработке больших файлов и необходимость повторной загрузки после ошибки.

Последовательная загрузка данных в БД достигается блокировкой PostgreSQL на время импорта и позволяет предотвратить одновременную загрузку одной и той же записи разными загрузчиками. Её обратная сторона - ожидание завершения предыдущего импорта.

## Реализация API и работа с БД

Для API я выбрал FastAPI, поскольку он поддерживает проверку запросов через Pydantic и имеет автоматическое создание документации. В API и импортёре использую общие входные модели, чтобы правила проверки данных совпадали. Я использую SQLAlchemy для описания таблиц и построения запросов, а вот для использования запросов независимо от HTTP-маршрутов я выделил их в отдельный модуль. Фиксацией транзакции управляет вызывающий код - это позволяет объединять несколько операций и откатывать их вместе. Синхронные маршруты соответствуют синхронной работе SQLAlchemy и позволяют обойтись без дополнительной сложности асинхронного подключения.

Для списка продаж и агрегатов я использовал общую функцию фильтрации для того, чтобы условия выборки совпадали. Агрегация выполняется в PostgreSQL, а список продаж возвращается страницами - это ограничивает объём данных, которые получает приложение из БД и передаёт клиенту.

## Тесты

Тесты выполняются на PostgreSQL, чтобы проверить поведение внешних ключей, обновления при конфликте и отката транзакций в выбранной СУБД. Загрузка полного CSV и его повторный импорт проверяют совпадение итогов с исходным файлом и отсутствие повторного добавления уже загруженных продаж.
